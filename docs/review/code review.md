你现在是一位非常严格、非常有经验的科研代码 reviewer 和实验诊断专家。请你对这个科研项目做一次“以性能问题定位和优化建议为目标”的深入 code review。

当前背景：
- 这个项目已经可以正常开始训练，不是完全跑不起来
- 但目前模型效果不理想，性能没有达到预期
- 我希望你不要只做表面的代码风格检查，而是深入排查：为什么效果不好，瓶颈可能在哪里，哪些地方最值得优先优化

你的核心任务：
1. 找出可能导致模型效果不佳的关键实现问题
2. 找出训练、验证、测试流程中可能影响结果可信度的设计缺陷
3. 检查方法设计与实际代码实现是否一致
4. 判断哪些问题最可能真正影响性能，哪些只是工程层面的小问题
5. 给出可执行的优化建议，并按优先级排序

请按下面流程工作：

第一部分：先建立项目理解
- 阅读仓库结构，概括各模块职责
- 总结项目的研究目标、输入输出、训练流程、推理流程、评估流程
- 标出核心文件、关键配置、关键脚本
- 用你自己的话描述：这个模型目前到底是怎么训练起来的

第二部分：以“性能不佳”为导向做深度审查
请重点检查以下方面：

A. 数据与样本流
- 数据集读取是否正确
- train / val / test 划分是否合理，是否存在泄漏或分布偏差
- preprocessing、normalization、augmentation、label 处理是否有问题
- batch 构成、采样策略、正负样本比例、shuffle 是否合理
- 有没有样本被错误过滤、重复使用、标签错位、时间对齐错误、模态对齐错误等问题

B. 模型与 forward 路径
- 实际 forward 路径是否与方法设计一致
- 各分支输出 shape、归一化、激活、融合逻辑是否合理
- 是否存在某个分支几乎没起作用、被旁路、被错误缩放或被错误 detach 的情况
- 是否存在 mask、padding、attention、fusion、projection 的实现错误
- 是否存在“代码能跑但信息流有问题”的 hidden bug

C. loss 与优化目标
- loss 的定义、权重、归一化、温度系数、mask 逻辑是否合理
- 多个 loss 之间是否存在冲突
- loss 是否真正作用到了想优化的模块
- 是否有某些 loss 名义上存在，但梯度实际上不起作用
- 是否有量纲不一致、权重失衡、极端稀疏监督、梯度过弱/过强的问题

D. 训练循环与优化器
- optimizer、scheduler、warmup、weight decay、gradient clipping、mixed precision、gradient accumulation 是否正确
- train / eval mode 切换是否正确
- EMA、BN、Dropout、LayerNorm 等行为是否在训练和验证阶段一致
- checkpoint resume 是否会破坏训练状态
- seed、cudnn、随机采样是否影响结果稳定性

E. 验证、测试与指标
- metric 的实现是否正确
- validation/test 阶段是否和训练假设一致
- 后处理、阈值、解码、采样策略是否不合理
- 有没有“训练目标和最终评估指标错位”的问题
- 是否存在只在部分样本上评估、错误平均、统计方式偏差等问题

F. 配置与实验管理
- 配置文件中的参数是否真的生效
- 是否有 hidden hard-code 覆盖 config
- 不同脚本之间是否存在默认值不一致
- README、脚本、配置、实际代码三者是否一致
- 是否存在“以为改了参数，其实没生效”的问题

第三部分：不要只找 bug，也要分析“性能为什么差”
请你从研究诊断角度回答：
- 当前项目效果不理想，最可能的前 5 个原因是什么
- 这些原因分别更像是：
  1) 实现 bug
  2) 训练策略问题
  3) 数据问题
  4) 方法本身瓶颈
  5) 评估问题
- 哪些问题最值得优先验证
- 如果我只能先改 3 个地方，你建议改哪里，为什么

第四部分：输出格式
请输出一份结构化报告，格式如下：

# 1. 项目整体理解
- 项目在做什么
- 核心训练链路
- 核心推理链路
- 核心评估链路

# 2. 最可能影响性能的关键问题（Top issues）
对于每个问题，请写清楚：
- 问题描述
- 所在文件 / 类 / 函数
- 为什么它会导致效果不好
- 这是高概率问题还是低概率问题
- 影响程度：高 / 中 / 低
- 修改建议

# 3. 严重实现问题（P0）
- 直接影响实验正确性或结果可信度的问题

# 4. 中优先级问题（P1）
- 影响性能、稳定性、复现性的问题

# 5. 次要问题（P2）
- 工程质量、维护性、可读性问题

# 6. 方法设计 vs 实际实现 不一致清单
- 明确列出“理论上想做什么”和“代码实际上做了什么”

# 7. 性能瓶颈假设排序
- 按“最值得先排查”的顺序列出前 5 个性能瓶颈
- 每个都说明依据

# 8. 最优先的优化路线
- 给出最建议优先执行的 3~5 项修改
- 尽量说明预期收益和验证方式

# 9. 可直接改动的补丁建议
- 对明确问题给出尽量具体的改法
- 必要时给伪代码或代码片段

额外要求：
- 不要只做表面 code style review
- 不要泛泛而谈，要尽量基于具体文件、函数、配置来分析
- 对于每一个“可能影响性能”的点，都说明它为什么会影响结果
- 如果你不确定，请明确写出不确定点和推断依据
- 请特别标出那些“代码能跑，但会 silently 拉低性能”的问题
- 如果你发现需要更多信息（如日志、曲线、配置、样本输出）才能判断，请明确指出还缺什么，以及这些信息能帮助验证什么
